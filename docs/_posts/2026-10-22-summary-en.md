**「Community discussion」** Commenters report strong real-world results: RobinL says 2.0 scales to roughly 128-192 vCPUs on EC2, where versions before 2.0 topped out near 64, and nicoritschel says he ran the alpha in production as a centralized analytics server for a small organization. ### [eMudhra CA keys crackable in milliseconds; trust stores must update](https://scotthelme.co.uk/eight-bits-of-trust-emudhras-ca-keys-cracked-in-milliseconds/) ⭐️ 8.0/10

Scott Helme reports that eMudhra&\#x27;s certificate authority keys can be cracked in milliseconds because of catastrophic key generation weaknesses. The finding affects widely trusted CA bundles, so operating systems, applications, and container images must ship updated trust stores; devices that cannot be updated remain exposed.

hackernews · hkc · Oct 21, 09:08 · [Discussion](https://news.ycombinator.com/item?id=50177916)

**「Background」** eMudhra is a certificate authority \(CA\) based in India whose role is to issue and vouch for digital certificates; according to reporting on the incident, eight of its intermediate certificates carried private keys that anyone can recover from the public certificate, a catastrophic key-generation failure. The researcher reported the issue to Apple, Google, Microsoft, Mozilla, and eMudhra on Saturday 17th October, and Chrome pushed a CRLSet update blocking the affected certificates that evening, with Firefox following via OneCRL a few hours later.

**「Impact」** Organizations and users must treat eMudhra&\#x27;s issued certificates as untrusted and update every trust store that includes the affected roots and intermediates, including browser, operating system, and application bundles such as OS ca-certificates and certifi, then rebuild container images that embed them. The compromise is tracked as CVE-2026-111943 and specifically affects Go applications that may continue to trust fraudulent certificates. Because eMudhra certificates were widely trusted by browsers, operating systems, and services such as Cloudflare, any deployment that cannot promptly receive the trust-store update remains exposed to certificates forged using these eight compromised keys.

**「Community discussion」** Wayne, the original reporter, said the weakness was found out of the box with Google&\#x27;s paranoid\_crypto and that a fuller audit of CCADB certificates found no further hits. Commenters debated the hard problem of unupdatable devices, with one suggesting the bad keys could enable jailbreaks for IoT devices and another remarking that having hundreds of trusted CAs was itself excessive.

### [PHP patches two critical unauthenticated RCEs in all supported branches](https://lwn.net/Articles/1102014/) ⭐️ 8.0/10

On October 21, 2026, PHP released versions 8.5.12, 8.4.27, 8.3.36, and 8.2.35 to fix two critical vulnerabilities that allow unauthenticated remote code execution: CVE-2026-109618 \(RCE via OOM corruption\) and CVE-2026-109619 \(RCE via stale global state\). All PHP installations serving web requests are at risk, including PHP-FPM, Apache with mod\_php, php-cgi, FrankenPHP, and LiteSpeed; mod\_php is considered highest risk because a demonstrated exploit can trigger before any application code runs. PHP versions older than 8.1 will not receive official updates, but the project has provided patch branches for PHP 7.4, 8.0, and 8.1 to help create backports.

rss · LWN.net · Oct 21, 13:53

**「Background」** These vulnerabilities lie in PHP&\#x27;s request lifecycle rather than in a specific extension or application. When a request is interrupted by out-of-memory handling, internal request data may be only partially initialized and later treated as valid; in the stale-global-state flaw, request-owned state can survive after its backing memory has been freed and be used by a later request on the same worker. Because the affected SAPIs expose PHP directly to HTTP traffic, an unauthenticated attacker can reach these code paths.

**「Impact」** Operators running PHP-FPM, mod\_php, php-cgi, FrankenPHP, or LiteSpeed should update to 8.5.12, 8.4.27, 8.3.36, or 8.2.35 promptly, with mod\_php deployments treated as the highest priority because the demonstrated exploit runs before application code executes. Linux distributions and vendors received patches in advance, so updated packages are expected soon; organizations still on PHP 7.4 through 8.1 will need to rely on vendor backports rather than official PHP releases.
